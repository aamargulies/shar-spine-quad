
Beating the binary search: Raspberry Pi 5, Apple M4 Max, two
generations of Intel Xeon, and an AWS Graviton 4

A few weeks ago I read Daniel Lemire's post on SIMD Quad search,
an algorithm that beats std::binary_search on sorted arrays of
16-bit integers by combining a quaternary interpolation search
with a SIMD block check. His benchmarks cover an Apple M4 and
an Intel Emerald Rapids server. I wanted to know what happens on
a smaller, slower machine: the Raspberry Pi 5. Then, once I had
the Pi 5 port tuned, I moved the code to my own M4 Max and
re-tuned it for Apple silicon, partly to see how much of the Pi 5
work transferred and partly because I wanted a fair same-algorithm
comparison of the two machines. After that I picked up access to
two x86 servers on EC2 - an older Intel Skylake-SP (Xeon 8175M)
and a modern Emerald Rapids (Xeon Platinum 8559C) - and ported
the variant to AVX-512. The Intel chapter turned out to be two
chapters, because the same source file wants to compile into
noticeably different code on the two uarchs, and the decision
of which code to emit is not the obvious one. Finally I picked
up an r8g instance - AWS Graviton 4, an Arm Neoverse V2 server
core - and wrote a fifth variant for that. This post covers
all of it.

The Pi 5 has four Arm Cortex-A76 cores at 2.4 GHz, 128-bit NEON
vectors (no SVE), a 64 KB L1 data cache per core, 512 KB of L2
per core, 2 MB of shared L3, 64-byte cache lines, and LPDDR4X
memory. The M4 Max P-core is a different machine entirely:
128-byte cache lines, 128 KB L1D per P-core, 16 MB of shared L2
per P-cluster, three load AGUs, a very aggressive hardware
prefetcher, a big out-of-order window, and LPDDR5X unified
memory. Still 128-bit NEON - no SVE/SVE2 on Apple silicon either -
so the ISA is the same, but almost everything else about the
memory hierarchy has changed.

The short version of what I found: the same algorithm runs
roughly 4-6x faster on the M4 Max warm (bench_table.txt
n=4096: SIMD kernels 4.9-5.4x, std::binary_search 6.2x,
std::find 3.7x), which is unremarkable. The "cold" column
widens that gap to 13-30x at n=4096 (bench_table.txt), which I
originally took for the interesting part - but most of it is
the harness, not the core:
bench.cpp's cold pass has no cache flush, and the ~35 MB working
set stays in the M4's on-chip caches while it misses to DRAM on
the Pi 5 (see the note above). On the Intel side, Skylake-SP
turns out to punish the "obvious" AVX-512 port with a frequency-
license downclock (license level L1 for these light integer ops)
that makes the tuned variant slower than the generic SSE2
reference, and the fix is to emit different code for Skylake-SP
than for Emerald Rapids despite both being "AVX-512 capable."
More on that after the algorithm story.

Porting the reference algorithm to the Pi 5

The reference implementation has two paths guarded by #ifdef:
NEON for ARM, SSE2 for everyone else. The Pi 5 takes the NEON
path. The SSE2 branch is dead code and I removed it. I also
switched the block size from 16 to 32. The reasoning: on the Pi 5
a cache line is 64 bytes, which holds exactly 32 uint16_t values.
A 32-element block is therefore one cache line - if the array is
64-byte aligned - and a block check that touches exactly one line
is as cheap as it can be. (Caveat I did not check at the time:
the benchmark's std::vector arrays are only 16-byte aligned, so
about 75% of the blocks it measures straddle two lines, and an
interleaved aligned-vs-misaligned A/B on the Pi 5 later measured
a +14-30% cold penalty at n=4096 - corrections section 5. A
Roaring integration must align its container arrays and spines to
get the one-line block this post assumes.) Halving the block
count also shortens the interpolation phase by roughly one
iteration.

The block check itself uses two paired NEON loads (vld1q_u16_x2),
which maps to the A76's two load AGUs and lets the hardware issue
both halves of the block in the same cycle.

This gets us a respectable baseline. At 4096 elements, warm cache,
the Pi 5 variant is about 2.2x faster than std::binary_search and
1-3% faster than the reference algorithm. That's a port, not an
improvement, but it's where every further optimization starts.

Small arrays

In the first round of benchmarks the Pi 5 variant was actually
slower than std::find for 8-element arrays. That's embarrassing:
we have a SIMD algorithm that loses to a linear sweep at the
sizes where you'd most expect SIMD to shine. The reason was that
n=8 fell into the scalar fallback path (n < 32), so none of the
SIMD code ever ran.

The fix was to add two dedicated NEON fast paths. For 8 <= n < 16,
a single 128-bit vld1q_u16 + vceqq_u16 + vmaxvq_u16 covers the
whole array in three instructions. For 16 <= n < 32, a paired
vld1q_u16_x2 covers the first 16 elements and a short scalar
sweep handles the tail.

After this change n=8 dropped from 14.6 ns to 4.7 ns warm in the
development run (the archived 5-run median is 5.4 ns,
bench_table.txt). It is among the fastest cells in the whole
table.

What Eytzinger does to your thinking

The interpolation phase probes three scattered cache lines per
iteration. Those loads are on the critical path, and for cold
arrays at size 4096 they dominate the runtime. This is exactly
the kind of pattern that an Eytzinger layout would attack: pack
the upper levels of the search tree into the first few cache
lines so they're always hot, and prefetch the descendant log2(B)
levels ahead - the one whose block of B descendants fills exactly
one cache line (5 levels at gap 32, 6 at gap 64) - so its miss
overlaps with the work of the current level.

I didn't want to change the array layout - Roaring Bitmap
containers need to stay sorted for iteration, intersection, and
serialization - but I stole the prefetching idea. At the end of
each quaternary iteration, I compute the address of the next
iteration's middle probe (which is deterministic from the current
base and n, before we even know the outcome of the current
probes) and issue a __builtin_prefetch for it. The miss, if
there is one, now overlaps with the current iteration's in-flight
loads instead of serializing behind them.

At the time I recorded this as a 10-25% cold win for n >= 512 on
the Pi 5, and that claim travelled into every later document. It
was wrong. No prefetch A/B was ever archived, and the archived
main-bench table contains a built-in one: simd_quad_graviton.c
(introduced later in this post) is simd_quad_pi5.c minus this one
prefetch line, and on the Pi 5 the prefetch kernel is slower cold
at 13 of 14 sizes from n=128 up (+2% to +31%) and slower warm at
13 of 14 (5-run medians, bench_table.txt pi5 vs graviton rows;
per-run pairs in pi5_runs/rebench_run*.txt agree). Fresh
interleaved A/Bs during the 2026-10 review agreed (corrections
section 5). Structurally the prefetch address depends on the
just-updated base, so it issues at the same dependency depth as
the demand loads it is supposed to hide. The shipped Pi 5 kernel
still contains it, pending a kernel A/B at all sizes. Keep this in
mind for the M4 and Graviton chapters, where I "discovered" that
wide cores don't want the prefetch - the narrow one doesn't
either.

What orlp's bitwise binary search does NOT do

Around the same time I came across orlp's "bitwise binary search"
post. It reformulates binary search as building the answer one
bit at a time, with a fully branchless inner loop and beautiful
unrolling properties on power-of-two sizes.

It's a lovely piece of code. It's also almost completely
orthogonal to our problem. Bitwise binary search's whole appeal
is making a latency-bound scalar loop shorter. Our loop is not
latency-bound in the scalar sense - it's bandwidth-bound across
three independent loads per iteration, which the A76's two
load AGUs can overlap and the M4's three can overlap even more
freely. Swapping our quaternary descent for a bitwise binary
descent would give up that independence and serialize log2(n)
loads instead of parallelizing them. By that dependency-chain
argument it should be a wash on L1 and a regression on cold
cache - I did not benchmark it, so that is reasoning, not
measurement.

The one idea from orlp that transfers is compile-time unrolling
when the size is known. That's a general technique, not a
bitwise-binary one.

The idea that actually worked: a key spine

The cold-cache interpolation phase was still the Pi 5 bottleneck.
At n=4096 it touches up to ~10 different cache lines before the
final SIMD block check. The hardware prefetcher can't help - the
access pattern is data-dependent and irregular. Software prefetch
of the next middle probe was supposed to help a bit; as the
archived A/B above shows, it doesn't even do that.

The right move is to pack the probe keys themselves into a
separate, dense region. Given a sorted array carr of 4096
uint16_t values and a gap of 32, define:

    spine[i] = carr[(i+1)*32 - 1]

This is 128 uint16_t values, 256 bytes, 4 cache lines on the Pi 5
when the spine is line-aligned (a 16-byte-aligned std::vector
spine usually spans five). The entire interpolation phase - every
probe, every comparison - now reads from this tiny contiguous
region, which on cold access costs a handful of consecutive cache
lines whose misses can all be in flight at once, or one up-front
prefetch to pull in.

The final SIMD block check still loads from carr. The spine isn't
trying to replace the sorted array, only to accelerate the
pointer chase that precedes the block.

A small subtlety bit me the first time: at small cardinalities
(num_blocks <= 3) the spine-based code was slower than the
non-spine code. Why? Because the non-spine code's probes
accidentally touch the same cache lines the final SIMD block
will need - they prime the block load for free. The spine lives
in a separate region, which breaks that accidental reuse, and at
tiny num_blocks there aren't enough probes to pack. The fix is
to fall through to the plain Pi 5 path when num_blocks <= 3. It's
one if-statement. This same subtlety will come back when we port
to the M4, for the same reason.

With that guard in place, the spine variant is a huge win at
every size where it activates.

Pi 5 results

All Pi 5 numbers are nanoseconds per query on a Raspberry Pi 5,
Cortex-A76 @ 2.4 GHz, GCC 15 with -O3 -mcpu=cortex-a76. Each
benchmark generates 4000 random sorted arrays per size and
performs membership queries in warm mode (each array queried
5000 times consecutively, simulating cache hits) and cold mode
(each array queried once, cycling through thousands of arrays).
There is no explicit cache flush in cold mode; it relies on the
~35 MB cycle outrunning the caches, which it does on the Pi 5 for
n > 256 (at n <= 256 the set is L2/L3-resident even here) and
does not do on the larger-cache hosts later in this post
(corrections section 5).

First, the warm-cache picture:

The three SIMD variants cluster together at the bottom. The plain
Pi 5 port and the reference algorithm sit within a nanosecond or
two of each other - the 32-element block and the small-size fast
paths help a lot at small n, but by n=4096 we're all doing roughly
the same work. The spine variant pulls clearly ahead starting
around n=128 and stays ahead, ending at 22.5 ns versus 30.1 ns for
the plain Pi 5 variant and 31.1 ns for the reference at n=4096
(bench_table.txt, 5-run medians). That's a 1.3x improvement on a
workload that already felt optimized.

Now the cold-cache picture, which is the interesting one:

[bench_cold.png]

This is where the spine earns its keep - and the Pi 5 is the one
host where bench.cpp's cold column really is cold at these sizes:
the ~35 MB working set does not fit its 2 MB L3, so these are DRAM
misses (corrections section 5). Cold-cache queries at large n are
dominated by memory latency, not arithmetic. The reference SIMD
Quad and the plain Pi 5 variant sit just under 300 ns at n=4096
(296.3 and 299.0). The spine variant does the same query in
150.7 ns.

At n=4096 on the Pi 5 (bench_table.txt), the spine variant is
roughly 3x faster than std::binary_search warm (68.6 vs 22.5),
roughly 2x faster than std::binary_search cold (323.4 vs 150.7),
roughly 1.4x faster than the reference SIMD Quad warm (31.1 vs
22.5), and roughly 2x faster than the reference SIMD Quad cold
(296.3 vs 150.7).

The cold-cache improvement is the one I find most satisfying
because cold is the case that matters most. If your hot loop was
already cache-resident you probably wouldn't be searching an array
in the first place - you'd be doing something smarter with a hash
or a bitmap. Membership queries that hit cold data are where you
actually need the algorithm to be fast.

Moving to the M4 Max

I wanted to retune the code for my own machine, an M4 Max, for
two reasons. First, Apple silicon has a different memory
hierarchy and a different core, so I didn't expect the Pi 5
choices to carry over cleanly. Second, I wanted a same-algorithm
comparison of the two machines that wasn't confounded by
different compilers and different block sizes.

Three things change on the M4. The cache line is 128 bytes, not
64, which doubles the natural block size. The core has three
load AGUs instead of two, which gives the quaternary descent
even more headroom. And there's a much larger out-of-order window
plus a much more aggressive hardware prefetcher, which changes
the calculus for manual prefetch.

So I wrote simd_quad_m4. The plan:

Block size goes from 32 to 64. A 64-element block is one 128-byte
cache line on the M4 (when the array is 128-byte aligned; the
benchmark's 16-byte-aligned vectors straddle two lines 87.5% of
the time). The block check becomes two vld1q_u16_x4
loads (eight paired 128-bit loads total), which the three load
AGUs can interleave freely. The interpolation depth shrinks
again.

Small-size fast paths gain a new tier. The Pi 5 variant had
dedicated paths for n in [8,16) and [16,32). With gap=64 we need
one more, for [32,64), which uses a single vld1q_u16_x4 to cover
the first 32 elements and scalar-sweeps the tail.

Speculative prefetch inside the interpolation loop comes out.
At the time my reasoning was "it bought 10-25% cold on the Pi 5,
but the M4's OoO window is wide enough that the miss already
overlaps with other in-flight loads, so the instruction just
costs an issue slot." The second half may well be right; the
first half, as the Pi 5 chapter now says, was never true - the
prefetch loses on the A76 too. So the honest statement is
simpler: the in-loop prefetch costs more than it saves on every
host where it has been A/B'd (Pi 5 built-in A/B above, EMR and
GV4 A/Bs below). I left it out and the benchmarks agree.

Spine stays, and compresses further. With gap=64 and n=4096 the
spine is 64 uint16_t values, 128 bytes - exactly one M4 cache
line if it is 128-byte aligned (the benchmark's is not, so it
usually straddles two). The entire interpolation phase for the
maximum-size Roaring container now lives in one or two cache
lines. At n=2048 it's half a line. The num_blocks <= 3 fallback
from the Pi 5 variant applies here too, for the same
accidental-reuse reason.

The warm-cache comparison looks about how you'd expect. Every
algorithm runs roughly 4-6x faster on the M4 than on the Pi 5
(bench_table.txt n=4096: SIMD kernels 4.9-5.4x,
std::binary_search 6.2x, std::find 3.7x), and the ratio is
fairly uniform. Same ISA, same code, a much wider and faster
core. There's nothing much to say: the M4 is a bigger machine
and it does the arithmetic faster.

The cold-cache comparison is where it gets weird - and where the
harness fooled me.

At n=4096 cold, the same simd_quad_pi5 code runs 20x faster on
the M4 (15.2 ns) than on the Pi 5 (299.0 ns). The same gap=32
spine code runs 13x to 30x faster on the M4 (11.6 ns as
pi5+spine, 5.1 ns as the byte-identical graviton+spine) than on
the Pi 5 (150.7 / 154.7 ns). The warm ratio for the same
comparison is 5x. So "cold" work on the M4 looks 3-6x less
penalized than on the Pi 5, relative to warm.

You can see the same thing inside a single machine. On the Pi 5
at n=4096, the cold/warm ratio for the plain pi5 variant is
~10x (299.0/30.1). On the M4 it's ~2.5x (15.2/6.2). I originally
read this as "cold cache is genuinely a smaller problem on Apple
silicon - a big OoO window plus an aggressive hardware prefetcher
plus unified LPDDR5X is doing an enormous amount of hidden work."
Most of it is not that. bench.cpp's cold pass has no cache flush;
it walks ~35 MB of arrays in allocation order with the targets
the previous algorithm just used. That footprint fits the M4's L2
and SLC and does not fit the Pi 5's 2 MB L3. The Pi 5 column is
DRAM misses; the M4 column is on-chip cache hits. The ratio
measures cache capacity, not latency hiding. How much better the
M4 core actually hides a real DRAM miss is an open question that
needs a flushed cold column (corrections section 5).

This does not mean the spine stops mattering on the M4. On Pi 5
cold n=4096 the spine saves ~148 ns (299.0 -> 150.7), roughly
2x. On M4 cold n=4096 the spine drops the m4 variant from 16.8
to 6.5, roughly 2.6x, and the gap=32 kernel from 15.2 to 11.6
(or 11.7 to 5.1 for its identical twin). The spine is the single
biggest optimization in the stack on both machines, even when
the misses it removes are L2-to-SLC rather than DRAM: compressing
the pointer-chase region into one or two cache lines still
matters.

Two other cross-machine observations are worth pulling out.

First, gap=64 (the m4 block size) only edges out gap=32 (the pi5
block size) on the M4 at the largest warm sizes (4.3 vs 4.6 ns at
n=4096), and the cold column cannot separate them (see above).
The extra interpolation step saved is tiny, and the spine-size
advantage of the smaller gap (more keys packed per line for large
n) almost cancels it. If I had to ship one variant to run on both
machines, I'd ship pi5+spine: it's within 10% of m4+spine warm on
the M4 and dominates on the Pi 5. That surprised me - I expected
the M4 retune to be a clearer win on its own hardware.

Second, the speculative __builtin_prefetch in the quaternary
loop: I believed it was the right call on the A76 and the wrong
call on the M4, and built a tidy story about memory-level
parallelism on top - two load AGUs and a modest OoO window leave
room for a software hint on the A76; three AGUs, a deeper window
and a smarter prefetcher saturate the useful MLP on the M4. The
archived data say it was the wrong call on both (Pi 5 chapter
above). The story's second half may still describe the M4; its
first half is not supported, and the "which uarch properties flip
this decision" question the Intel chapter set out to answer turns
out to have a boring answer: nothing measured so far wants this
prefetch.

Moving to x86: Intel Skylake-SP and Emerald Rapids

The two ARM variants share an ISA and are structurally very
similar. Going to x86 meant writing a new file, simd_quad_intel.c,
and it meant thinking about a problem the ARM ports didn't have:
different generations of x86 with nominally the same ISA
extension behave very differently in practice.

The two hosts:

  Intel Skylake-SP     Xeon Platinum 8175M, family 6 model 85.
                       AVX-512F/BW/DQ/VL/CD. No VBMI2. 64 B cache
                       line, 32 KB L1D, 2 load AGUs. Shared EC2
                       tenancy, which makes cold numbers noisy
                       enough that every reported cell is the
                       median of 5 ./bench 4000 5000 runs.

  Emerald Rapids       Xeon Platinum 8559C, family 6 model 207,
                       Raptor Cove cores (5th Gen Xeon Scalable).
                       AVX-512 plus VBMI2, VNNI, BF16, FP16, AMX.
                       64 B cache line, 48 KB L1D, 3 load AGUs.
                       Deeper ROB, more LFBs, more aggressive L1
                       streamer, newer P-core.

Both run the same simd_quad_intel.c source with -march=native.
What comes out of the compiler is the interesting part.

The first draft, and why it was wrong on Skylake-SP

The first draft followed the shape of the Pi 5 port. gap=32,
because the Intel cache line is 64 B and 32 u16 values is exactly
one line (for a line-aligned array) - the same structural argument
that sized the A76 block.
The 512-bit register made the block check trivially nicer than
on either ARM variant: one load, one compare, one kortest. Three
hot instructions where the Pi 5 had four and the M4 had eight.

    __m512i needle = _mm512_set1_epi16((short)pos);
    __m512i v = _mm512_loadu_si512((const void *)blk);
    __mmask32 m = _mm512_cmpeq_epi16_mask(v, needle);
    return m != 0;

This should have been the easy win. It wasn't. On Skylake-SP the
plain "intel" variant (non-spine) was slower than the reference
SSE2 simd_quad at n >= 2048 warm in my development runs (I did
not archive that A/B, so treat the magnitude as anecdote). I
rebuilt twice assuming I'd fumbled a flag. The build was fine;
the problem was the uarch.

On Skylake-SP, executing a 512-bit operation trips the core into
a lower frequency license for a window measured in hundreds of
microseconds. For the light integer ops a zmm block check uses (a
load and a compare) that is license level L1; L2 is reserved for
heavy FP/multiply work. This is well-documented. What's less
well-known is how badly it interacts with code shaped like ours:
the block check is one zmm instruction per call, but the
quaternary interpolation loop surrounding it is entirely scalar.
That scalar loop now runs at the reduced frequency, and on SKX
the reduction is large enough to more than cancel the
one-instruction block-check win. Net: worse than SSE2. (To be
explicit about what follows from the fix below: the shipped SKX
build executes no 512-bit instruction at all, so nothing in the
Skylake numbers in this post is downclocked.)

Newer Intel server parts - Ice Lake-SP, Sapphire Rapids, Emerald
Rapids, Granite Rapids (a later generation than my EMR host; the
8559C itself is Raptor Cove) - have this penalty either hugely reduced
or gone entirely. But you can't distinguish "licensed-downclock
uarch" from "non-licensed uarch" with the AVX-512BW feature flag:
Skylake-SP has AVX-512BW. You need a feature flag that landed
after the licensing changed.

VBMI2 is that flag. It shipped first in Ice Lake - which is also
the first generation where the AVX-512 frequency penalty is
negligible. Skylake-SP has BW but not VBMI2. Ice Lake-SP /
Sapphire / Emerald all have VBMI2, as does the later Granite
Rapids. This makes
__AVX512VBMI2__ a good proxy for "safe to emit a zmm
instruction inside a scalar hot loop" - with two footnotes: AMD
Zen 4 and Zen 5 also define VBMI2, so the proxy selects the zmm
path there too, untested; and -march=x86-64-v4 does not define
it, so that build line silently produces the AVX2 + prefetch
variant (corrections section 5).

So the Intel variant's block check is gated:

  #if defined(__AVX512VBMI2__)
      // VBMI2 present - Ice Lake-SP or newer. Single-compare
      // zmm path, three instructions, kortest on the mask.
      __m512i needle = _mm512_set1_epi16((short)pos);
      __m512i v = _mm512_loadu_si512((const void *)blk);
      __mmask32 m = _mm512_cmpeq_epi16_mask(v, needle);
      return m != 0;
  #else
      // VBMI2 absent - Skylake-SP or AVX2-only. Two 256-bit
      // loads + cmpeq + or + movemask. Same structural shape
      // as the Pi 5's paired NEON load.
      __m256i needle = _mm256_set1_epi16((short)pos);
      __m256i v0 = _mm256_loadu_si256((const __m256i *)blk);
      __m256i v1 = _mm256_loadu_si256((const __m256i *)(blk + 16));
      __m256i eq = _mm256_or_si256(_mm256_cmpeq_epi16(v0, needle),
                                   _mm256_cmpeq_epi16(v1, needle));
      return _mm256_movemask_epi8(eq) != 0;
  #endif

On -march=native, GCC picks the right side automatically. Skylake
gets AVX2. Emerald Rapids gets the zmm fast path.

With that gate in place, the "intel" variant goes from losing to
SSE2 on Skylake to modestly winning, and Emerald Rapids gets to
use the instruction it actually wants to use.

n=4096 warm, intel+spine is 26.8 ns, versus 33.0 ns for the
reference and 82.3 ns for std::binary_search (bench_table.txt).
The intel spine variant is about 1.2x faster than the reference
SIMD and about 3.1x faster than std::binary_search on warm cache.

The cold picture is where SKX falls furthest behind. Corrections
section 5 counts it among the hosts whose last-level cache holds
bench.cpp's ~35 MB working set, so this is an unflushed LLC-hit
column here as on EMR and GV4, not a DRAM-miss one - though the
8175M's 33 MB L3 is close enough to that footprint that I would
want a flushed cold column before leaning on the label (my own
inference, not the corrections file's). Shared EC2 tenancy adds
noise on top. Cold queries at n=4096 are expensive here:
binary_search is 276.8 ns, reference SIMD is
171.5 ns, intel is 180.9 ns, intel+spine is 132.7 ns. The spine
is still the biggest win (1.36x over the non-spine intel
variant), but absolute numbers are much larger than on the M4.
The ordering is mostly what you want - every spine variant beats
its non-spine sibling, everything beats binary_search - though
the non-spine intel kernel does not beat the SSE2 reference cold
here. This is not a host where the SIMD tricks feel
transformative. They're just reliably ahead of the generic path.

Emerald Rapids results

Same harness, per-cell median of 5 runs on EC2. Emerald Rapids is
notably quieter than Skylake - warm columns barely move between
runs. Here the block check is the single-zmm path.

[bench_emr_warm.png]

[bench_emr_cold.png]

This is a different machine. At n=4096 warm, intel+spine is 18.0

At n=4096 cold, EMR's intel+spine (37.2 ns) is 3.6x faster than

unflushed harness (corrections section 5), one on a bare-metal

comparisons from this column compare cache levels, not cores. So
it says little about the two cores; my earlier framing of it as
"different memory subsystems, six years of uarch in between" is

cold column. Second, SKX's and the Pi 5's cold cells (132.7 and

does with a real DRAM miss is not measured here.

The prefetch question, revisited on Intel

I thought the A76 loved the speculative prefetch and the M4
didn't need it, with Intel somewhere in between on paper. In
practice, each uarch deserves its own A/B - and the A76's, once
read off the archived data, says it doesn't love it either.

On Skylake-SP the A/B was inconclusive: shared-tenant noise
swamped the effect. At the time I used a uarch tiebreaker:
Skylake's 2 load AGUs and narrower OoO window are "exactly the
conditions where a software prefetch has room to pay its issue
slot back - the same story as the Pi 5, another 2-load-AGU core
where the prefetch bought 10-25% cold." That precedent no longer
exists (the Pi 5 prefetch is a net loss in the archived data),
and the other argument I leaned on elsewhere - that SKX's scalar
loop runs downclocked under the AVX-512 license - is not true of
the shipped build, which issues no zmm. So the SKX prefetch stays
in because its one A/B was inconclusive under shared-tenant noise;
a repeat on quiet hardware is open (not among the items corrections
section 6 tracks).

On Emerald Rapids I could settle the A/B. Two binaries, same
source, the only difference being the presence or absence of the
_mm_prefetch line in the quaternary loop. Five runs of each,
per-cell medians (emr_runs/baseline_run{1..5}.txt vs
emr_runs/noprefetch_run{1..5}.txt):

  n     intel warm  intel cold
  512     -6.2%      -18.5%
  1024    -3.8%       -4.1%
  2048   -13.0%        0.2%
  4096    -4.0%       -1.6%

Negative numbers are prefetch-removed being faster. Every warm
cell at n >= 512 moves; the biggest warm win is -13% at n=2048.
The cold n=512 win is -18.5%. There are no regressions anywhere
worth naming. The spine columns are noise-band in both directions,
which is expected - the spine variant never had the in-loop
prefetch in the first place.

The mechanism is the same one that made the M4 uninterested in
prefetch: EMR's ROB is deep enough, its load AGUs (three of them)
are plentiful enough, and its L1/L2 streamers are aggressive
enough that the miss is already being overlapped with the current
iteration's in-flight work. The software hint is dispatch
bandwidth spent for nothing.

So the prefetch is gated on the same __AVX512VBMI2__ flag, with
opposite polarity to the block check:

  #if !defined(__AVX512VBMI2__)
      _mm_prefetch((const char *)(carr + (base + (n>>1)) * gap),
                   _MM_HINT_T0);
  #endif

One source file, one compile, two uarchs, two different bodies
of code. The same generational boundary controls both decisions.

One experiment that didn't pan out: gap=64

EMR has three load AGUs and a deep OoO window, so the "what
about gap=64" thought was hard to resist. A 64-element block on
a 64-byte-line machine spans two cache lines, which is exactly
why I'd argued for gap=32 in the first place - but maybe EMR's
memory-level parallelism swallows the second line for free, and
the shorter interpolation wins.

Same A/B methodology: two binaries from the same source, median
of five runs each. Non-spine and spine, at the usual sizes. The
result, as a delta vs. gap=32:

  n      warm plain  warm spine  cold plain  cold spine
  256     -53%        -55%        -26%        -22%
  512     +45%        +67%        -26%        -17%
  1024    -49%        -54%        -18%        -15%
  2048    +54%        +64%        -14%         -3%
  4096    -46%        -48%        -17%        -24%

Not noise. Read down the warm columns and the sign alternates:
-53, +45, -49, +54, -46. The explanation is the interpolation
iteration count. At n=512 and n=2048, gap=32 lands a lucky
iteration (fewer quaternary steps happen to resolve without a
final binary step); gap=64 ties on iteration count but pays the
two-cache-line block-check cost. At n=256, n=1024 and n=4096
gap=64 actually saves an iteration, and the win is large.

Cold cache tells a cleaner story: gap=64 is uniformly faster
across the board, because the interpolation-path shortening
matters more than two-line cost on cold data. But the warm
regressions at n=512 and n=2048 are too large to ignore -
both are common Roaring container sizes - and so gap=64 is not
shippable for this workload. Keep gap=32.

The conclusion is the mirror of what I found on the M4 Max.
There, gap=64 was right because the cache line was 128 B; a
single (aligned) block still fit in one line. On EMR, gap=64
spans two lines, and the iteration-count win is size-dependent. The
original cache-line argument was right.

Graviton 4: the ARM server case

The two x86 hosts are separated by five years of uarch. The two
ARM hosts we've seen so far are separated by an even bigger gap:
a 2.4 GHz Cortex-A76 in a $80 single-board computer versus a P-core
in a $3500 laptop. I wanted one more ARM data point that sat where
Intel Emerald Rapids sits: modern, server-class, cloud-hosted.
AWS Graviton 4 is the obvious candidate. It's a 96-core chip
built on the Arm Neoverse V2 core, which is structurally the
widest ARM core any of us can currently rent in any quantity.

The uarch facts, alongside the ARM hosts we already have:

  Pi 5 / A76         2 load AGUs, 64 B cache line, 64 KB L1D,
                     128-bit NEON, small OoO window, no SVE.

  M4 Max P-core      3 load AGUs, 128 B cache line, 128 KB L1D,
                     128-bit NEON, very wide OoO, aggressive HW
                     prefetcher, no SVE.

  Graviton 4 / V2    3 load pipes (the review's count; I had
                     written 4 - not verified on hardware here,
                     corrections section 5), 64 B cache line,
                     64 KB L1D, 128-bit NEON + 128-bit SVE2, very
                     wide OoO, aggressive L1/L2 streamers.

Two things to notice. First, Graviton 4 has the A76's 64-byte
cache line, so gap=32 is the right block size for the same
structural reason as on the Pi 5. Second, although V2 supports
SVE2, the vector length is 128 bits - the same as NEON. There is
no register-width advantage to picking up SVE2 for this problem,
and staying on NEON keeps the source identical in shape to the
two other ARM variants. I wrote simd_quad_graviton.c as a
NEON-only file.

The one interesting design question was the speculative prefetch.
The A76 keeps it (on the strength of a "10-25% cold win" that, as
the Pi 5 chapter now says, the archived data do not support). The
M4 Max drops it and doesn't miss it. On paper, V2 looks more like
the M4: wide OoO, plentiful load pipes, aggressive streamers. So I
shipped the variant without the prefetch and A/B'd against a
scratch version that kept it. Five runs of each, per-cell medians
(gv4_runs/ab_summary.txt, non-spine kernel). Negative percentages
mean the prefetch-kept version was faster; positive means removing
it (what the shipped code does) was right.

  n     gv4 warm  gv4 cold
  128     +5.9%     +3.2%
  256     +2.0%     +5.6%
  512     +8.9%     +1.8%
  1024    +1.9%     +4.1%
  2048   +10.8%     -2.5%
  4096    +4.0%     +0.7%

Every warm cell at n >= 128 moves in the same direction, with the
biggest hit at n=2048 (+10.8%) and n=512 (+8.9%). Cold is similar
direction with a single small outlier. No configuration where
keeping the prefetch is clearly faster. So V2 lives in the same
regime the M4 and EMR do: a SW prefetch is dispatch bandwidth
spent for nothing. When I first wrote this up I drew a line:
"every wide-OoO core I've tested (M4, EMR, V2) wants the prefetch
out; every narrower one (A76, SKX) wants it kept - the split is
OoO width plus load-AGU count." The second half has collapsed.
The A76's built-in A/B says out; SKX's A/B was inconclusive. On
the evidence, every host wants this prefetch out, and the "narrow
cores want it" rule was a story fitted to one unarchived number
(corrections section 5).

At n=4096 warm, simd_quad_graviton + spine lands at 16.2 ns.
That's 2.9x faster than std::binary_search (47.1 ns) and 1.2x
faster than the plain graviton variant (20.0 ns) - but not faster
than the gap=16 reference SIMD, which is 15.2 ns warm at this

n=4096 cold, the spine variant lands at 34.6 ns versus 119.8 ns
for binary_search, 81.7 ns for the reference, and 65.0 ns for the

reminder that on GV4 (like EMR and the M4) that column is an

Two observations worth pulling out.

First, Graviton 4 is nearly tied with Emerald Rapids on this
workload. At n=4096 warm, gv4+spine is 16.2 ns vs emr+spine
18.0 ns. At n=4096 cold, gv4+spine is 34.6 ns vs emr+spine
37.2 ns (both LLC-hit regimes in this harness). These two hosts
are running entirely different ISAs
(AArch64 with NEON vs AVX-512 with VBMI2), different SIMD
register widths (128 bits vs 512 bits), different block-check
instruction counts (four NEON compares + OR-tree vs one zmm
cmpeq), and they end up in the same place. The algorithm's
bottleneck is memory, not arithmetic. When two cores have
comparable memory-level parallelism (OoO width, load AGUs, L1
bandwidth, prefetcher aggressiveness), the benchmark lands in
the same band regardless of what their SIMD instructions look
like.

Second, Graviton 4's cold n=4096 cell (34.6 ns) is about a
quarter of Intel Skylake-SP's (132.7 ns) despite the ARM host not
having anything wider than 128-bit NEON and the x86 host having
AVX-512BW. I originally read this as a core-generation story
("CPU generation matters more than vendor"). The harness cannot
support that reading: both cells are last-level-cache hits in
bench.cpp's unflushed cold column (corrections section 5), SKX's
on a shared-tenant box, and cross-host "cold" comparisons from
that column compare cache levels, not cores. The 4x gap is
unexplained pending a flushed cold column. What survives is the
narrower point that register width is irrelevant to this column;
what the two cores do with a real DRAM miss is not measured here.

Compile-time n=4096 on Graviton 4

I also ported the compile-time-n=4096 specialization over from
the Intel variant. At gap=32 and n=4096 the quaternary descent is
exactly three iterations (128 -> 32 -> 8 -> 2), and every offset
is a compile-time constant, so the compiler can emit a
straight-line body with no backward branches. The first version
finished with one binary step and the final lo pick; the shipped
version (the "hybrid") replaces those two dependent rounds with
one branchless 2-probe finish,
lo = base + (spine[base] < pos) + (spine[base+1] < pos).

My first measurement of the unroll on Graviton 4 was a modest
warm win (16.19 -> 13.96 ns, -13.8%) with a cold delta of similar
size (37.63 -> 32.07 ns, -14.8%) that I read as noise
(gv4_runs/spineN_summary.txt, 5-run medians; the "16.2 -> 14.6 ns"
of the first draft was an unarchived development run), smaller
than on EMR, and I blamed V2's branch predictor. The shipped
hybrid is a different animal: on GV4, 16.22 -> 7.00 ns warm
(-57%) and 35.86 -> 30.62 ns cold (-15%) against the general-n
spine in the same runs (gv4_runs/hybrid_summary.txt, 5-run
medians); on EMR, 17.86 -> 6.50 warm (-63.6%) and 37.20 -> 24.36
cold (-34.5%) against the same-run general-n spine
(emr_runs/shipped_summary.txt, 5-run medians). On SKX it is -32%
warm in 5/5 runs, but slower cold in 3 of 5 runs (per-run -12% to
+62%, paired per-run median +40%) against a general-n control
stable to +-0.6% in the same runs, so the SKX hybrid may carry a
real cold cost; not settled at 5 runs (skx_runs/hybrid_run{1..5}.txt;
corrections section 2.3). It is the right thing to ship for API
callers that know their container is full-sized (4096 u16 = 8 KB =
the classic Roaring array container cap), and on the server hosts
its warm win is several times the spine's own (EMR: spine -8%,
hybrid -64% at n=4096).

What I learned

First, the biggest win (the spine) came from Eytzinger's layout
idea, not from its branchless-descent idea and - as it turned
out - not from its prefetch idea either. The received wisdom
about Eytzinger is that it's "branchless binary search with
prefetch." What transferred here was the layout: put the keys
the descent touches into a few contiguous lines. The in-loop
software prefetch I borrowed alongside it is a net loss on the
Pi 5 (above), and a real Eytzinger outer with the Khuong-Morin
prefetch, once its prefetch offset was fixed, never beats the
outer spine on the Pi 5 in the two-level benchmark (corrections
sections 1 and 6). The spine is the biggest optimization in the
cold column on every host, and the biggest general-n
optimization warm; the compile-time hybrid built on top of it is
the biggest warm win on the servers.

Second, orlp's bitwise binary search looks like a general
improvement to binary search but is not one. It's a
specialization to a particular regime (scalar, serial,
power-of-two, lower-bound semantics). When your algorithm is
already parallel across loads, the bitwise trick is the wrong
trade. I did not benchmark it; by the dependency-chain argument
above it should be a wash in L1 and lose cold.

Third - and this is the one I should have expected - the
optimization wasn't in the algorithm. It was in the memory
layout. The SIMD Quad algorithm is already close to what any of
these cores can physically do per cycle. The only thing left to
optimize was where the bytes live. The spine is 256 bytes of
redundant data per 8-kilobyte container on Pi 5, SKX, and EMR
(all 3% overhead with 64 B lines), or 128 bytes on the M4
(1.5%, 128 B line). On every machine it is the biggest single
speedup in the stack, and on every machine it wins for the same
reason: cold pointer chases through scattered lines lose to a
read of a few contiguous lines.

Fourth, the cold-cache gap between Apple silicon and the Pi 5
is much larger than the warm-cache gap - but I now know that
most of that is cache capacity meeting an unflushed harness, not
Apple's core hiding latency (see the M4 vs Pi 5 section). The
same goes for "Emerald Rapids is closer to the M4 than to
Skylake-SP in this respect": EMR's, the M4's and SKX's cold cells
are all on-chip cache hits in that column and only the Pi 5's are
DRAM misses (corrections section 5), so the column does not rank
the three cores. What survives: on the Pi 5, any code path that
misses L1 has a large, visible cost, so data-layout tricks pay
well; on the M4 and EMR the spine still pays, even when the misses
it removes are L2-to-SLC rather than DRAM. You should still write
cache-aware code on the newer machines. How much less you are
rewarded for it is a question for a flushed cold column.

Fifth - and this is the one I genuinely didn't see coming - ISA
feature flags are a poor model of performance. AVX-512BW is on
paper the same on Skylake-SP and on Emerald Rapids, but the
cost of emitting a zmm instruction inside a scalar loop is so
different between the two that the same source compiled the
same way produces an improvement on one host and a regression
on the other. The fix was to find a more specific flag -
__AVX512VBMI2__, which happens to draw the line where Intel's
own uarch cost model changed - and gate on that. What was
pleasantly surprising is that the same flag, with opposite
polarity, turned out to be a workable switch for the
speculative-prefetch question too: the generations that are safe
to use zmm are the ones where the prefetch was A/B'd out. Whether
the no-VBMI2 side should keep it is, as the Skylake section says,
unmeasured - so "one flag, two decisions, one cut line" is one
decision and one default.

Sixth, the speculative-prefetch "split" I thought Graviton 4
had clarified does not exist. The story was: A76 and SKX (narrow
OoO, 2 load AGUs) want the prefetch; M4, EMR and V2 (wide OoO,
3+ load pipes) don't; the rule is MLP budget, not vendor or ISA.
The V2 data point was real, but the "keep" side was built on an
A/B that was never archived (Pi 5) and one that was inconclusive
(SKX). The archived Pi 5 data say the prefetch loses there too.
So the evidence supports a simpler, less interesting rule: this
particular prefetch - whose address depends on the just-updated
base and therefore issues at the same dependency depth as the
loads it is meant to hide - does not pay on any host measured.
The gating lesson survives in weaker form: __AVX512VBMI2__ still
cleanly separates the zmm decision on x86, and it happens to also
switch the prefetch off on the hosts where it was A/B'd out; on
ARM there is no such flag, so per-host files remain the simplest
way to make per-host calls.

I suspect we can do even better than this. Since this post was
first drafted, two of the obvious next steps have been done: the
compile-time n=4096 hybrid now exists on every host, and the
two-level (container-key outer + n=4096 inner) benchmark runs on
all six hosts under a 4-mode harness. Its paired results are in
Text/corrections_2026-10.md sections 2 and 6; the short form is
that a branchless Shar outer (variant F) wins hot on five hosts
(-14% to -54% vs the outer-spine variant D; 5/5 runs on hot_bat
on all five and on hot_ser on four, SKX 4/5), is 4/5 at -6% on
the Pi 5 in the archived runs and a tie there in the repaired
10-run harness (pi5_runs/twolevel_paired_v2.txt), while cold the
branchy or spine outers (C, D) are usually best - and on the Pi 5,
after that repaired harness, the recommendation is D outright. Our
stack beats Lemire's published variant in all 24 n=4096 cells (-35%
to -84% hot, -7% to -45% cold), but his is faster at several small
container sizes on the M4 Max. Still open: remove the Pi 5 in-loop
prefetch (needs a kernel A/B); align container arrays and spines to
cache lines; give bench.cpp a real cache flush; look at whether the
tail-block scalar sweep can merge into the SIMD path without
branching; and see whether AMX on Emerald Rapids has anything to
offer (probably not for 16-bit integers, but worth a look). Let
us get creative.
