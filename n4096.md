Right reasoning, but n=4096 is structurally a *boundary*, not a *mode*, in CRoaring — which makes "lots of n=4096 containers" less likely than intuition suggests:

- Array containers cap at `DEFAULT_MAX_SIZE = 4096`. At cardinality 4097 they convert to **bitset containers** (a 65536-bit bitmap, 8 KB), which uses a direct bit lookup — `simd_quad` is never called on them.
- So workloads dense enough to have lots of n=4096 containers tend to have *bitsets* instead. The arrays you do call `simd_quad` on are the ones that didn't make it to the bitset threshold.
- Sparse workloads → small arrays (n « 4096). Dense workloads → bitsets. n=4096 is the narrow strip where a container is dense enough to almost convert but doesn't.

That said, two reasons it's not zero:

1. **Bulk-loaded data** (deserialized bitmaps, snapshots) often clusters near boundaries because the threshold is fixed across all CRoaring deployments — many natural distributions pile up there.
2. **`run_optimize`-d containers** can stay as arrays past where they'd otherwise convert, depending on run-encoding economics.

**The n = 4096 caveat.** All of the above are two-level results with every container at n = 4096. They do *not* transfer to "every array container size from ~64 up to 4096": the M4 Max F-vs-Lemire size sweep (`m4_runs/sweep_fvl_raw.txt`, 200 sizes, 5 runs, `m4_fvl_sweep_data.py`) shows Lemire faster than F, by paired per-run analysis (`m4_runs/sweep_fvl_paired.txt`, 2026-10-11), at n = 48–62 (hot_bat, 25–29%, 5/5 at every size), n = 81–128 (hot_bat, 5–32%), n = 1–7 (cold_ser, 41–47%) and n = 60–156 (cold_ser, 6–36%), with narrower wins at a few other sizes below 256. On the Pi 5 (campaign `sweep_fvl2`, `pi5_runs/sweep_fvl2_raw.txt`, 179 sizes, 10 runs, 2026-10-11/12, against both the 2026-04-27 and the revised 2026-10-02 kernel) F wins hot at essentially every size and Lemire is ahead only in cold_ser below n ≈ 265 (`pi5_runs/sweep_fvl2_findings.md`), so the hot bands are a gap-64 (M4/M1) matter; the outer × inner square (`sweep_fvl3`, 2026-10-12, 10 runs, `pi5_runs/sweep_fvl3_findings.md`) attributes the Pi 5 cold_ser deficit at 33–265 to the outer search (the branchy `std::lower_bound` saves a flat 45–110 ns per query cold and costs a flat 18–33 ns hot, with either inner) and at n = 4096 puts the spine inner at ~100 ns hot and 260–360 ns cold per query against Lemire's (10/10 hot, 8–10/10 cold) with the Shar outer at +17/+31 ns hot (0/10) and −67 ns cold_ser (9/10). The code explains the bands: the gap-64 kernel's [32,64) path is one vector load plus a scalar sweep of up to 31 elements, the general tail scans up to 63 elements, and the spine is inert below n = 256 on 128-byte-line hosts (below 128 on 64-byte-line hosts) because `num_blocks <= 3` delegates to the plain path (`Text/corrections_2026-10.md` §2.3). So the honest version of this paragraph is: at n = 4096, F beats Lemire in all 24 host × mode cells (5/5 in 21, 4/5 in 3); across the real container-size distribution the small-container bands are open work (a size-dependent dispatch or a shorter scalar tail for n < 128).

If you want to actually answer the question, the path is: instrument a CRoaring deployment (Druid/ClickHouse/Pinot have telemetry hooks) to histogram array-container cardinalities at query time. Memory note from 2026-05-14 already flags this as an open question for the CRoaring upstream.
