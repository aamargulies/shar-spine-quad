# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Read `Text/corrections_2026-10.md` before quoting any number from this file or from the write-ups.** A full review on 2026-10-11 found four measurement/aggregation defects under most of the published comparisons (mis-aimed Eytzinger prefetch, ratio-of-medians across drifting runs, pre-2026-05-13 two-level cold numbers, unarchived 22-size plot curves). The kernels are correct and the large effects are real; the comparisons in this file were rewritten from paired per-run analysis. Where this file and the corrections document disagree, the corrections document wins.

## Project goal

Produce machine-optimized variants of the "SIMD Quad" search algorithm for sorted `uint16_t` arrays (sizes ~1–4096, as used in Roaring Bitmap containers). Eight hosts: Raspberry Pi 5 (Cortex-A76; two boards, "trixie" and "eight"), Apple M1 Pro (Firestorm), Apple M4 Max, Intel Skylake-SP (Xeon 8175M), Intel Emerald Rapids (Xeon 8559C, Raptor Cove cores), AWS Graviton 4 (Neoverse V2), since 2026-10-12 Intel Coffee Lake (Core i9-9980HK in the user's 2019 MacBook Pro "i9", hostname mb2019, Ubuntu; a Skylake-class client core, AVX2 only; host tag `cfl`, `cfl_runs/`), and since 2026-10-13 Intel Ice Lake-SP (two Xeon Platinum 8375C in the user's AWS i4i.32xlarge "big", Amazon Linux 2023; Sunny Cove cores, AVX-512 with VBMI2, so the zmm path; host tag `icx`, `icx_runs/`). Each CPU-family variant lives in its own `.c` file; `bench.cpp` is arch-aware and builds only the variants relevant to the host.

Always refer to Intel hosts by microarchitecture ("Intel Skylake", "Intel Emerald Rapids", "Intel Coffee Lake") — they share `simd_quad_intel.c` but take different SIMD paths (AVX2 on SKX and CFL, zmm on EMR). On ARM, refer to cores by microarchitecture ("Cortex-A76" / "Firestorm" (M1) / "M4 P-core" / "Neoverse V2"). M1 Pro and M4 Max share `simd_quad_m4.c` (both 128-B-line / wide-OoO Apple P-cores); all M4 design decisions port to M1 Pro with no code changes. Pi 5 and Graviton 4 share every spine kernel byte for byte (see Files).

## Files

- `simd_quad.c` — reference. Bare function body (no `#include`s, uses `constexpr`, `bool` without `<stdbool.h>`), `#include`d into `bench.cpp` and `bench_twolevel.cpp`. Two paths via `__ARM_NEON`: NEON for ARM, SSE2 for x86.
- `simd_quad_pi5.c` — Cortex-A76. gap=32, two `vld1q_u16_x2` loads + four `vceqq` block check, small-size fast paths [8,16)+[16,32), no in-loop prefetch since 2026-10-13 (the one speculative `__builtin_prefetch` per quat-loop iteration was removed after the dedicated A/Bs — see Findings; the plain kernel now compiles to the same instructions as `simd_quad_graviton`), spine + `simd_quad_pi5_spine_{256,512,1024,2048,4096}` compile-time specializations. High-foot sizes {256, 1024, 4096} are hybrids (straight-line unroll + branchless 2-probe finish `lo = base + (spine[base] < pos) + (spine[base+1] < pos)`); low-foot {512, 2048} are pure unrolls. `_spine_4096` IS the hybrid; prior unroll retired.
- `simd_quad_m4.c` — Apple M4 Max **and** M1 Pro. gap=64 (one 128-B cache line when aligned), two `vld1q_u16_x4` loads + eight `vceqq` block check, small-size fast paths [8,16)+[16,32)+[32,64), no prefetch, spine + `simd_quad_m4_spine_4096` (hybrid: 2 quat iters + branchless 4-probe finish). num_blocks=64, no binary tail (only gap=64 host). Single source file serves both Apple hosts.
- `simd_quad_intel.c` — Intel server. gap=32, AVX-512 single-compare block check gated on `__AVX512VBMI2__` with 2× 256-bit AVX2 fallback on SKX; no in-loop prefetch on either path since 2026-10-13 (the AVX2 path kept one "because the SKX A/B was inconclusive" until the Coffee Lake A/Bs settled it, see Findings; the spine kernels still prefetch their first spine line). The partial last block of the general-n kernels (plain, spine, padded spine) is checked with one vector membership test of the array's last 32 elements since 2026-10-17 (the "vector tail", adopted after the Coffee Lake and Ice Lake-SP kernel A/Bs; an empty tail returns false without loading; exhaustively checked on both paths). Spine + `simd_quad_intel_spine_{256,512,1024,2048,4096}` (same hybrid/unroll shape as Pi 5). Note `-march=x86-64-v4` does **not** define `__AVX512VBMI2__`; use `-march=icelake-server` or `-march=sapphirerapids` for the zmm path. Zen 4/5 define VBMI2 and will take the zmm path untested.
- `simd_quad_graviton.c` — AWS Graviton 4 / Neoverse V2. After comment stripping, every `simd_quad_graviton_spine*` function is identical to its `simd_quad_pi5_spine*` twin, and since the Pi 5 kernel dropped its in-loop prefetch (2026-10-13) the plain kernels compile to identical instructions too; the only code difference between the two files is the `_spine_padded` variants (present only here). Plain NEON, no SVE intrinsics. The `pi5s`/`gv4s` and now the `pi5`/`gv4` columns of `bench` therefore measure the same code (built-in noise gauges).
- `bench.cpp` — correctness + benchmark driver. `__ARM_NEON`/`__aarch64__` vs `__x86_64__` selects paths. ARM gets 9 algo columns (linear, binary, simd, pi5, pi5s, m4, m4s, gv4, gv4s). Canonical run `./bench 4000 5000`. Prints `4096*` A/B rows; on ARM `pi5_spine_4096` is timed twice at n=4096 (spine_N block and cross-host block) — the aggregators (`{host}_runs/compute_medians.py`, `reproduce.sh`) use the last (cross-host) row. **The "cold" column is LLC-flushed since 2026-10-11**: `thrash_llc()` (512 MB stride-64 write, the same flush as `bench_twolevel.cpp`) runs before every cold pass, outside the timed region, and the bench prints a `# cold column: …` provenance line (build-time override `-DQUADSEARCH_THRASH_BYTES`). Every archived main-bench run except `pi5_runs/rebench_flushed_run1.txt` (`rebench_run*.txt`, `hybrid_run*.txt`, `shipped_run*.txt`, `fullsweep_run*.txt` and the other bench-format `*_run*.txt` families; none of them carries that line) predates the flush: there the arrays were walked in allocation order with the targets the previous algorithm had just used, and the ~35 MB footprint fits every LLC except the Pi 5's, so their cold column is a DRAM miss on the Pi 5 at n > 256 only (L2/L3-resident at n ≤ 256 there) and an L2/L3/SLC hit on the other five hosts — a fair within-host A/B, not a cross-host comparison. The flush is verified to evict on the Pi 5 only; on each other host inspect the first flushed run (small-n cold cells at DRAM latency) before quoting a cross-host cold number. The first flushed Pi 5 run (2026-10-12, one run, GCC 17.0.0 20260704) puts the n=8 cold cells at 38–74 ns (archive 5–18) and the n=4096 spine cells 1.3–1.5× above the archive; its warm cells match the archive's fast mode at every size, but its `linear` column is 2.5–3.5× faster than the archive from n=64 up because that compiler auto-vectorizes `std::find` — a toolchain change, not the flush (the archive was built with GCC 15 per the `plot.py` provenance comment; the run files themselves record no compiler, the flushed-run header does). Ten more flushed runs followed on the second board "eight" (`pi5_runs/rebench_flushed_eight_run{1..10}.txt`, 2026-10-12/13, GCC 17, kernel blob f7c140b8 = still with the prefetch; drift 1.00× warm / 1.14× cold; paired analysis `pi5_runs/rebench_flushed_eight_paired.txt`, write-up `pi5_runs/rebench_flushed_findings.md`; `plot.py` carries their medians as the `pi5_flushed_*` dicts on their own two figures). The `plot.py` main-bench dicts and the PNGs derive from those pre-flush runs; do not mix flushed output into them (comment above `bench_cold`). **Since 2026-10-12 every size also prints an `nA` row**: the same columns on copies of the arrays and spines aligned to the host's cache line (64 B; 128 B on Apple hosts) with their sizes rounded up to it, measured right after the plain row, so each plain/aligned pair is a within-run A/B of the alignment (`aligned_copy`, `AlignedRef`; the n = 8 pair is the control, nothing straddles there). Parsers keyed on `<digits> |` rows skip the `nA` rows; `compute_bench_paired.py` reads them. The flush count per run is therefore 426 on ARM / 243 on x86 (~213 GB / ~122 GB written). Flushed campaigns are driven by `run_bench_flushed.sh HOST RUNS [BINARY]` (header lines `date / host / machine / command / build / compiler / governor / temp_before`, then `exit` and `temp_after`; never overwrites; `BENCH_TAG` names a second board's files, e.g. `rebench_flushed_eight_run{R}.txt`).
- `bench_twolevel.cpp` — 512 containers × 4096 inner, 4-mode harness (`hot_bat` / `hot_ser` / `cold_bat` / `cold_ser`). Variants A–G = {bsearch, outer spine, Shar} outer × {general-n, compile-time n=4096, Shar} inner; H/I = Eytzinger outer with Khuong & Morin line-prefetch (1-based layout, `kPrefOff = kGap/2`, line-aligned array, pad `kGap·(K+1)`) × {general-n, compile-time n=4096} inner; Lem = Lemire's published variant (bsearch outer + `simd_quad` inner, gap 16, no spine). argv: `[num_sets] [hot_reps] [mode hb|hs|cb|cs|all] [order_seed]`; a non-zero `order_seed` shuffles the order in which variants are timed within each mode pass (rows still print A..Lem). An untimed warm-up pass precedes the hot modes; `thrash_llc()` (512 MB) precedes every cold measurement. **"hot" means outer-hot, inner first-touch**: each set's 200 reps touch ~91 distinct containers once, so inner loads are DRAM-cold on Pi 5/SKX and L2/L3 hits on Apple/EMR/GV4 (F hot_bat on Pi 5: 61 ns at 12 sets, 213 ns at 200). Hot queries are ~50% outer misses; cold queries are 100% crafted hits. Arch flags: x86 default; ARM default (M4/M1, gap=64); `-DQUADSEARCH_ARM_PI5` (gap=32 + Pi 5 inner); `-DQUADSEARCH_ARM_GV4` (gap=32 + GV4 inner). Repaired 2026-10-11 (prefetch offset, pad, alignment, warm-up, order seed, thrash size); H/I numbers from before that date on any host are invalid. Since 2026-10-13 `-DQUADSEARCH_TWOLEVEL_ALIGNED=64` (128 on Apple) adds six twin variants Aa..Fa — A..F with the inner kernel reading line-aligned copies of every array and spine, made in a second pass and checked byte for byte, with a `# layout:` residue-histogram line and `aligned_twins=` in the header — and `QUADSEARCH_THRASH_BYTES` is honoured (a non-default flush prints a `# thrash_bytes:` warning line); `compute_twolevel_paired.py` detects extra rows and pairs each twin with its plain variant (campaign `pi5_runs/twolevel_v2_aligned_run*.txt`, `twolevel_paired_v2_aligned.txt`, write-up `pi5_runs/twolevel_aligned_findings.md`).

## Build

```sh
# Apple M4 Max
clang++ -O3 -mcpu=apple-m4 -std=c++20 bench.cpp simd_quad_pi5.c simd_quad_m4.c simd_quad_graviton.c -o bench

# Apple M1 Pro (shares simd_quad_m4.c)
clang++ -O3 -mcpu=apple-m1 -std=c++20 bench.cpp simd_quad_pi5.c simd_quad_m4.c simd_quad_graviton.c -o bench
# bench_twolevel uses the default ARM gap=64 path (no -D flag), same as M4 Max:
clang++ -O3 -mcpu=apple-m1 -std=c++20 bench_twolevel.cpp simd_quad_m4.c -o bench_twolevel

# Raspberry Pi 5
g++ -O3 -mcpu=cortex-a76 -std=c++20 bench.cpp simd_quad_pi5.c simd_quad_m4.c simd_quad_graviton.c -o bench
g++ -O3 -mcpu=cortex-a76 -std=c++20 -DQUADSEARCH_ARM_PI5 bench_twolevel.cpp simd_quad_pi5.c -o bench_twolevel

# AWS Graviton 4 (Neoverse V2)
g++ -O3 -mcpu=neoverse-v2 -std=c++20 bench.cpp simd_quad_pi5.c simd_quad_m4.c simd_quad_graviton.c -o bench
g++ -O3 -mcpu=neoverse-v2 -std=c++20 -DQUADSEARCH_ARM_GV4 bench_twolevel.cpp simd_quad_graviton.c -o bench_twolevel

# Intel w/ AVX-512 + VBMI2 (Ice Lake-SP, Sapphire/Emerald/Granite Rapids). NOT -march=x86-64-v4 (no VBMI2).
g++ -O3 -march=sapphirerapids -std=c++20 bench.cpp simd_quad_intel.c -o bench

# Intel Skylake-SP/X (family 6 model 85): AVX-512BW but no VBMI2; zmm gated off, -march=native picks the AVX2 path.
g++ -O3 -march=native -std=c++20 bench.cpp simd_quad_intel.c -o bench

# Intel / AMD AVX2-only (Haswell through Raptor Lake, Zen 1-3). Zen 4/5 define VBMI2 and take the zmm path untested.
g++ -O3 -march=haswell -std=c++20 bench.cpp simd_quad_intel.c -o bench

# Intel Coffee Lake (i9-9980HK, the "i9" MacBook Pro under Ubuntu, GCC 17 in /usr/local/bin): -march=native
# resolves to skylake (AVX2, no AVX-512), so simd_quad_intel takes the 2x ymm block check (no in-loop prefetch since 2026-10-13).
```

## Findings that should shape future work

- **The spine is the single biggest optimization on every machine.** Pi 5 cold n=4096 ~2×; M4 ~3×; Intel/GV4 similar. Mechanism: the descent reads a contiguous 256 B instead of chasing probes through the 8 KB array (memory-level parallelism across the few spine lines), not a stride prefetcher — a 256 B spine is too short to train one.
- **The Pi 5 in-loop prefetch was a net loss in the main bench and was removed on 2026-10-13.** `simd_quad_graviton` was `simd_quad_pi5` minus the prefetch line, so the Pi 5 bench's pi5 vs gv4 columns were the A/B: in the pre-flush archive the prefetch kernel was slower cold at 13 of 14 sizes from n=128 up and slower warm at 13 of 14 (`plot.py` pi5 dicts), and the "~10–25% cold win" previously stated here had no supporting measurement. The dedicated A/Bs of 2026-10-12/13 settled it: in ten paired flushed main-bench runs on the second board (`pi5_runs/rebench_flushed_eight_paired.txt`) the prefetch kernel is slower warm at every size from 128 up (+3% to +8%, 10/10 at every one of the 14 sizes; the identical-code gauge pi5s vs gv4s ties at all 22) and slower cold at 12 of those 14 sizes (WIN-strength at 7: +4% to +23%, e.g. 617 +23%, 2048 +13%, 4096 +5% — equivalently the no-prefetch kernel is 4–18% faster, 617 −18%, 2048 −12%, 4096 −5%), faster only at 1024 cold (−7%, 9/10, the one WIN for the prefetch) and marginally at 1234 (−2%, 8/10, a TIE); in the two-level kernel A/B (`sweep_ab1`, Gnp vs G) it was 3–14% *faster* in the outer-hot modes from n ≈ 667 and 3–8% slower in both cold modes — a regime trade in that harness, a loss in both regimes of the main bench. Structurally the prefetch targeted the start of block `base + n/2` while the next probe reads the end of a block (same line only if `carr` is 64-B aligned and n % 4 ∈ {0, 1}), with an address depending on the just-updated `base`, i.e. at the same dependency depth as the demand loads. The line is gone (the comment in the loop records the numbers); the Pi 5 and Graviton plain kernels now compile to identical instructions. Removed on M4/EMR/GV4 by measurement earlier, and from the Intel AVX2 path (Skylake-SP, Coffee Lake) on 2026-10-13 after the Coffee Lake A/Bs (bullet below).
- **gap tracks cache line, not SIMD width.** Even with 512-bit registers, Intel gap=32 is right because the line is 64 B — a 64-element block spans two lines. Caveat: the one-line property needs an aligned `carr`; a Roaring integration should align container arrays and spines.
- **gap=64 is not shippable on EMR or GV4.** Scratch `simd_quad_intel_gap64` (2026-04-30) was uniformly faster cold (−14 to −26%) but alternated sign warm: at n=512/2048, gap=64 was 45–67% *slower* warm. Same pattern on GV4. Scratches not committed.
- **M1 Pro ports from M4 Max with zero code changes.** gap=64 / 128-B line / wide OoO / 3 load pipes all shared. Absolute numbers ~1.4× slower than M4 (M1 Pro clock ≈ 0.72× M4 Max).
- **The Apple `_spine_4096` cold "structural regression" (+188–212%) may be a measurement-order artifact.** In the pre-flush `bench.cpp` the spine kernel's cold pass ran right after the non-spine kernel's cold pass with identical targets (block line = L2 hit on Apple's 12–16 MB L2), while the `4096*` row ran after its own 32 MB warm sweep (block line from SLC/DRAM). The gap matches L2-hit vs SLC-hit latency and the same asymmetry reproduces on the Pi 5. The 2026-05-14 decomposition on M1 Pro (full hybrid ~33.5 ns, descent-only ~8 ns, demand block load ~25 ns) is consistent with either explanation. Untested on Apple hardware with an explicit flush — `bench.cpp` flushes before every cold pass since 2026-10-11, so a re-run of `./bench 4000 5000` on M1/M4 is the test; do that before any further remediation (the OpenEvolve / sentinel / pfC efforts targeted this).
- **SKX AVX-512 frequency license.** On 8175M the non-spine `intel` path with zmm enabled lost to SSE2 at n ≥ 2048 warm; light 512-bit integer ops move SKX to license L1 (not L2 as previously stated), which lowers the clock of the surrounding scalar loop. Gate zmm on `__AVX512VBMI2__` (Ice Lake-SP+), not `__AVX512BW__`. In the shipped gated build no zmm executes, so "the scalar loop is downclocked anyway" is not a reason to keep the SKX prefetch.
- **Graviton 4 tracks the wide-OoO pattern (M4), not A76**, despite 64-B lines: warm n=4096 ≈ 16.2 ns, cold ≈ 34.6 ns (5-run medians, `gv4_runs/rebench_run*.txt`). Prefetch dropped. Its spine kernels are the Pi 5's code.
- **Every host ships the hybrid at n=4096.** The hybrid (3 quat + branchless 2-probe finish, or 2 quat + 4-probe finish on gap=64) saves one dependent load-use round vs the retired unroll. Warm deltas (per-cell medians of 5): EMR −54.8%, SKX −28.9%, Pi 5 −16.9% (paired per-run median −31.0%), M1 −4.4%, M4 −2.6% (paired −1.1%; one cell differs by 0.01 ns, so call M4 a tie). **SKX caveat:** the hybrid is −32% warm (5/5) vs the general-n spine but +40% cold (paired per-run median; per-run −12%, +62%, +41%, +40%, −6%, hybrid faster in 2 of 5 runs) against a general-n control that is stable to ±0.6% in the same runs (`skx_runs/hybrid_run*.txt`), so "shared-tenant noise" does not explain it; the SKX hybrid may have a real cold cost. The earlier "~−1.5% warm on SKX" described the retired unroll.
- **Compile-time `_spine_{256,512,1024,2048,4096}` family lives on GV4 / EMR / Pi 5.** GV4 medians vs general-n: warm −22 to −63%, cold −15 to −35% except n=2048 (+17%, weak: 4/5 with one −31.7% run). SKX: family ported, per-size A/B not run.

- **Methodology lessons (apply to every future measurement).** (1) Compare variants within a run and report sign counts + paired medians; never difference per-variant medians. (3) Randomise variant order (`order_seed`) and warm up before the first timed variant. (4) Record governor and temperature. (5) A cold cell of 200 queries is ~300 µs on the Pi 5 — one interrupt is a 10–50% error; cold verdicts need many runs. (6) Never overwrite an archived run file. (7) Before trusting a new variant's first cell, ask what else differs besides the factor under test: in the Pi 5 kernel A/B of 2026-10-12 the line-aligned variant read 44–67% slower than the baseline hot at n = 1 before any kernel difference could matter, because a line-aligned copy of a 2-byte array occupies a full line and 51,200 of them leave the L3 (a footprint effect, real for a line-aligned allocator but not an alignment effect), and a descriptor whose fields straddle two lines looked like a culprit until the layout A/B showed it costs almost nothing. Record such effects with the campaign and read small-n cells of a layout-changing variant as footprint, not as the kernel. (8) In a multi-variant hot pass, variants that share storage refresh it for each other: in `bench_ab_pi5.cpp` five of six variants read the plain arrays and only Fa its copies, so the plain arrays were touched one or two passes before being timed and Fa's copies six passes before — worth 4–17 ns against Fa in the "hot" (first-touch-within-a-pass) modes and the whole of the `sweep_ab1` alignment penalty (`pi5_runs/layout1_findings.md`). Give every variant its own storage (as `bench_layout_pi5.cpp` does) or thrash before every variant. (9) A two-binary A/B has identical-code cells too, and they are the gauge: on Coffee Lake the WIN rule fired on 6.5% warm / 7.0% cold of 215 identical-code cells, with unanimous 10/10 signs up to +7% at n = 47–89 from code placement alone (`compute_bench_ab.py --effect`, `cfl_runs/bench_ab_pfab_vs_pfab_np_paired.txt`); an effect cell counts only where its |median| clears the gauge's largest at the same size, and a 10/10 sign below 128 on identical code is ordinary, not evidence.

## Code shape caveats

- `simd_quad.c` is a bare function body — `#include`d into `bench.cpp` and `bench_twolevel.cpp` inside a TU with the right arch header already in scope. Don't compile standalone.
- `simd_quad_m4.c` uses `vld1q_u16_x4` (NEON-only, AArch64-only). Shared between M4 Max and M1 Pro — any change needs re-benchmarking on both.
- `simd_quad_graviton.c` is plain NEON (no SVE). Compiles on any AArch64 host; linked on all ARM hosts. Its spine kernels are byte-identical to the Pi 5's — change both or neither.
- `simd_quad_intel.c` requires AVX2 (`#error` otherwise). zmm fast path via `__AVX512VBMI2__`: `-march=icelake-server`, `-march=sapphirerapids` enable it; `-march=x86-64-v4` and `-march=skylake-avx512` do not.
- Compile-time `_spine_N` kernels take no cardinality and have no guard: a wrong-size input reads out of bounds or returns a silent false negative. Callers must dispatch on exact cardinality.
- Laptop warm numbers get flaky under thermal/frequency hops. Plug M4 into AC. On the Pi 5 pin with `taskset` and record the governor (`ondemand` by default).

## Normal workflow

1. Edit one of the `simd_quad_*.c` files (or add a new one).
2. Rebuild with the appropriate command above.
3. `./bench 4000 5000` — correctness check prints `correctness: ok` then the table.
4. For two-level comparisons: `./run_twolevel.sh HOST 10`, then `compute_twolevel_paired.py`; quote paired medians with sign counts.
5. If adding a new dataset to plot, append to `plot.py` (only values derivable from an archived run file, with a provenance comment) and `python3 plot.py` to regenerate PNGs + `bench_table.txt`.
